# ららくろそふとQA 開発の記録

企画書（[design.md](design.md)）が「何を作るか」の資料なら、これは「**どういう流れで作ったか**」の記録。
次のゲームを作るときに、進め方の参考にするために残している。

- 書く人: くろすけ（ららすけと相談しながら）
- 更新のタイミング: 作業の区切りごと（何かを作った・決めた・テストプレイの感想をもらった とき）
- 細かい日々のやりとりは claude-memory の `worklog/` にもある。ここは「あとから読んで流れが分かる」ことを優先してまとめる

---

## 全体の流れ（ここまで）

```
アイデア → 方向性の相談 → 企画書 → リポジトリ作成
  → 試作①（作中ゲーム＋バグ）→ ②（オフィス画面・仕様メモ）→ ③（報告書）→ ④（1日の流れ）
  → テストプレイ1回目 → 改善 → テストプレイ2回目 → 改善 → …
```

ポイントは **「小さく作る → 公開URLで触ってもらう → 感想で直す」をくり返した**こと。
企画書の段階で決めきれなかったこと（返事のタイミング、修正確認、採点など）は、遊んでみてから決まった。

---

## ステップごとの記録

### 0. アイデア

- **きっかけ（ららすけ）**: 「自分はゲームのQAに携わってるから、バグを見つけるゲームを作ったら面白いかなーって思った」
- くろすけが方向性を4案（間違い探し型／バグ入りミニゲーム＋報告／カードゲームのログの裁定ミス探し／QA業務シミュレーション）出して比べた
- **決定**: 「全部楽しいから4（QA業務シミュレーション）まで目指したい」→ 段階を踏んで近づける

### 1. 方向性を固める

- ららすけが**実際のQAの流れ**を教えてくれた（仕様書 → テスト設計 → 項目書 → 実行 → 不具合検知 → 再現確認 → 報告 → 開発の返答 → 修正確認と影響範囲 → クローズ）。世間のイメージ（壁にぶつかり続ける）とのギャップもテーマに
- 「作中でテストするゲームをどうするか」で3案 → **今まで作ったゲーム（神経衰弱・スイカ・スロット・カードゲーム）を作中タイトルにする**＋**版が育つ**要素
- 舞台は**ららすけの今の仕事＝モバイルゲームの運営QA**（日替わりで色々なタイトルのイベントを見る）
- 進め方は「企画書 → 1日目の試作」

> 💡 コツ: 最初に「全体像 → 選択肢 → おすすめ」で話すと、方向が早く決まる。現場の知識（ららすけの経験）が一番の材料になった

### 2. 企画書とリポジトリ

- 企画書のたたき台 → 未決事項を1つずつ決める（タイトル「ららくろそふとQA」、1日＝朝昼夕の3ターン、報告書は選ぶだけ、見た目はオフィス風）
- `godot-web-game-template` から `rarakuro-qa` を作成。`main` に push すると GitHub Pages に自動で公開される
- 企画書には**決定事項の表**と**改訂履歴**をつけた → あとで「いつ・誰が・何を決めたか」が分かる

### 3. 試作① 作中ゲーム＋バグ3つ

- 元の神経衰弱（memory-match）のコードを流用し、ハロウィン絵柄8種を図形で描いた
- **バグを「データ」で持つ**（`data/bugs.json`：ID・起きる条件・症状・期待する動き・重要度）。ゲーム側は「このIDがONならわざと間違える」分かれ道を置く
- 開発用の**バグON/OFFスイッチ**で、正しい動きと見比べられるようにした
- 自動テスト（バグONとOFFで動きが変わるか）とスクショで確認してから渡した

### 4. 日本語フォントとルールの1行

- **ららすけの感想**: 「3枚めくれるのが少し分かりづらいかも。2枚めくって絵柄をそろえるゲームって最初に書いておく（あえて書くことをヒントにする作戦）」「日本語表示できた方がいい」
- Noto Sans JP を使う文字だけに絞って（サブセット化）9.5MB → 2.6MB で同梱
- 盤面の下に「カードを2枚めくって、同じ絵柄をそろえよう！」

> 💡 コツ: 画面に「本来のルール」を書いておくと、プレイヤーが「おかしい」と気づく手がかりになる

### 5. 試作② オフィス画面と仕様メモ

- ヘッダー（会社名・何日目の朝昼夕）、リーダーからのチャット、モニターの中に作中ゲーム、机に「仕様メモ」ボタン
- **ららすけ案**: 仕様メモに使っている絵柄を並べる → 「キャンディが無い、かわりにFがいる」に気づける
- 仕様メモの中身もデータ（`data/spec_*.json`）

### 6. 試作③ 報告書

- 選ぶだけの報告書（どこで／再現手順／何が／期待する動き／実際の動き／重要度）
- 判定: 実際の動きでバグを特定 → 修正します／再現しません／仕様です／重複です
- **「本当に見た？」**: 画面で見ていないバグは報告できない（選択肢からの当てずっぽう対策）→ ららすけ「ほんとに見た？のところがいい」

### 7. 試作④ 1日の流れ

- **ららすけの疑問**: 「報告を出しても朝から動かない」→ まだ作っていない部分だった（説明不足を反省）
- **ららすけ案**: 「朝出した報告は昼に返事、直ったバグは次のターンから直ってる。夕方までに3つ正解できなかったら残業ターン」→ 企画書の「返事は翌日」から変更
- 「見たバグ」はターンごとにリセット → ららすけ「修正が入ったら前のビルドで見たことは当てにならない、はリアル」

### 8. テストプレイ1回目 → 改善

- **ららすけの感想**: テンポ・残業は違和感なし。要望は3つ
  1. **修正確認フェーズ**: 開発の返事 → リーダー「まずは直ってるか確認しよっか」→ 同じ操作でバグが出ない →「修正確認完了！」→「ほかに不具合がないか探そう」。最後は「終業前」で確認
  2. 結果画面に「もう一度1日目」と「次の日へ」
  3. **報告書を1項目ずつ**（全部見えると推測できる）＋ダミーを増やす → **起きないバグ候補をデータに足してダミーにする**
- 決め方: くろすけが選択肢を出して、ららすけが選ぶ（確認するまで報告できない／2日目は準備中で置く／起きないバグを足す）

### 9. テストプレイ2回目 → 改善

- **ららすけの感想と案**:
  - 絵柄違いの重要度は現場なら「中」、ゲームでは「低」でもいい → **どちらも正解**に
  - **採点方式**にしてピッタリ当てたら高得点 → 1件100点、減点、ランク、ベストスコア
  - 重要度だけ違うなら正解・減点だけ
  - **手順が大事でないバグ**（画像・報酬はマスタ設定の修正）は手順が違っても直してもらえる
  - **1日目のバグを7つの中からランダムで3つ** → 何回も遊びたくなる
- くろすけからの追加: ランダムだと「クリアできなくなるバグ」も出るので、モニターに「再起動」ボタン

## 次のゲームで使えるコツ（まとめ）

1. **最初に全体像と選択肢を並べてから決める**。いきなり作り始めない
2. **企画書は1枚から**。決定事項と改訂履歴を残すと、あとで迷わない
3. **小さく作って、毎回公開URLで触ってもらう**。1ステップごとに push → 自動公開
4. **中身はデータに出す**（バグ・仕様メモ・その日の担当・報告書の選択肢）。増やすときにプログラムを触らなくていい
5. **自動テストとスクショで確認してから渡す**。直したら別の所が壊れた、を早く見つけられる
6. **遊んでみると設計が変わる**。変わったら企画書も直す（決定事項・改訂履歴）
7. **作っている途中の部分は「まだ作ってない」とはっきり伝える**（④の前に「報告しても進まない」と混乱させてしまった）
8. **作る人の経験が一番の材料**。今回はららすけの現場の感覚（重要度・マスタ設定・修正確認の流れ）がゲームを一気にリアルにした
